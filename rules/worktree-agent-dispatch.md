# Worktree sessions — subagent dispatch paths

- When a session works in a git worktree (EnterWorktree or `git worktree add`), subagent working directories do NOT reliably follow the session: dispatches have resolved relative paths against the MAIN checkout. Observed in practice: one writer type applied its edits to the user's active branch while another writer type in the same session resolved to the worktree.
- Every dispatch brief in a worktree session MUST use absolute paths under the worktree root and state "do not resolve paths relative to your working directory".
- Before every write dispatch, snapshot `git status --porcelain` in BOTH the worktree and the main checkout (plus `git diff` for any already-dirty file the dispatch could plausibly touch); after the dispatch, compare both trees against those snapshots before reporting the work done — a post-only check cannot detect contamination of an already-dirty file.
- Every write-dispatch brief tells the writer that other agents and the user may have live changes in the tree: it must preserve unrelated edits and must NOT use broad restore, reset, checkout, or stash operations (`git restore`, `git reset`, `git checkout --`, `git stash` in any form). The stash and `checkout --` bullets below are the evidence for this general rule.
- **Enforced by hook in Claude Code, when installed.** The optional `.claude/hooks/git-guard.sh` (PreToolUse, Bash; parser in `.claude/hooks/git-guard.py`) blocks, for the main thread and subagents alike:
  - `git stash`, except the read-only `list` and `show`;
  - `git restore`, `git reset` and `git clean -f`;
  - `git checkout -- <path>`, `.`, `-f`, `-p`, `<tree-ish> <path>`, and `<path>` for an existing or deleted tracked file;
  - `git switch --discard-changes` or `-f`;
  - pull, rebase and merge that would autostash: `--autostash`, or a true `rebase.autoStash` / `merge.autoStash` from `-c`, `--config-env` or the effective config (`--no-autostash` or `-c rebase.autoStash=false` allows; `--continue`, `--abort` and the other in-progress actions are never blocked);
  - `git worktree remove --force`.

  Quoted text, comments and heredoc bodies are not matched, except a heredoc or here-string a shell reads as its script (`bash <<EOF`, `bash <<< '…'`, `cat <<EOF | sh`) and `$(…)` in an unquoted body; a group piped to a shell (`(cat <<EOF; echo) | bash`) counts too. `$(…)` is checked with the cwd reached at its command. python/node/perl/ruby code from `-c`/`-e` or stdin is scanned for exec calls (`subprocess.run`, `os.system`, `execSync`, `system`, backticks) whose arguments are string literals; computed arguments and script files are not followed. The hook's own git queries run with lazy fetch and transports disabled, so a crafted repo cannot run code through it. Redirections such as `2>&1` are ignored. It fails open (allows) when `python3` is missing or the parser errors. The user can still run any of these with `! git …`. The Codex twin stays instruction-only. Regression cases: `.claude/hooks/cases.txt`. Without the hook installed, this rule is instruction-only in Claude Code too.
- Telltale of a wrong-tree write: an edit fails with "file does not exist" for a file that only exists in the worktree.
- Recovery: export the misapplied diff as a patch, `git apply` it in the correct tree, then reverse exactly those hunks in the wrong tree with `git apply -R <patch>` — never `git checkout --` the affected files (that restores each whole file from the index, destroying any pre-existing uncommitted edits in it) and never blanket-revert (the other tree may hold another session's live work).
- Write-dispatch briefs into a tree carrying uncommitted multi-phase work MUST prohibit `git stash` (including scoped `git stash push -- <file>`): a scoped stash reverts the file's ENTIRE uncommitted diff, not just the agent's own edit. Observed in practice: a writer's red-check stash of one file momentarily reverted earlier phases' uncommitted work in it. Prescribe Edit-based call-site disable/restore for red checks instead.
- **The wrong-cwd hazard is NOT worktree-specific — it bites in plain single-checkout sessions too.** Observed in practice: a writer whose targets all sat under a nested run folder (`docs/runs/<YYYY-MM-DD-slug>/`) wrote its own files into a stray nested `.claude/` tree inside that folder instead of the repo root. Nothing failed and the agent's report claimed success, so the report carries no signal. **Prescription:** writers never create per-agent memory directories under `.claude/`, and every write-dispatch brief says so; knowledge changes go to `docs/agent-knowledge/` only through an explicitly owned file. At verification time, treat an untracked `.claude/` directory anywhere below the repo root as a wrong-cwd write — move any genuinely-needed content into its proper owned location and delete the stray tree rather than committing it.
- **Concurrent writers over one doc set need a state recheck at BOTH ends of each run.** Observed in practice: writers dispatched in parallel over disjoint file sets, one briefed to record facts its siblings were still producing, found every one of those facts absent at its first grep and present at its last. A brief that says "record X as already true" must tell the writer to verify X before writing AND again immediately before reporting; a single snapshot is not the run's truth. Disjoint file sets make parallel writers safe for the TREE, not for cross-file CLAIMS.
